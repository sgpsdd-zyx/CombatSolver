## 1. 用户实际需求

我在玩《杀戮尖塔 2》的多人合作模式，**只有我一个人安装 CombatSolver，其他玩家照常手动玩，不安装这个 Mod，也不需要配合输入计划**。我是房主或加入方时都应能使用。

我希望 Mod 根据当前战场，帮助我更聪明地决定自己的出牌顺序、攻击目标、格挡、能力铺垫、选牌和用药。它应该帮助我存活并推进整队获胜，能识别击杀、集火、控制和支援队友的价值。

目前已经能运行，但我对实际建议质量仍不满意。此前有明显的过度防御问题；调整后仍需研究更好的策略或算法。本次没有提供新的失败战斗日志，因此不能直接断言剩余问题的具体根因。

产品边界如下：

- 我手动点击计算，参考建议后自己操作。多人模式不自动出牌、用药、选牌、结束回合或自动重新计算。
- 搜索可以在本地模拟队友的可能行为，作为研究候选，但不能把这些行为当成队友承诺，也不能操作真人队友或依赖他们装 Mod。
- 已发生的队友行为及当前状态应正常纳入；队友未来怎么打属于外部不确定性。
- 我此前接受的打法偏好是：每个回合约 1～3 HP 损失可以接受，在合理风险下尽量打出有价值的输出。这个数字不是要求每回合主动掉血。
- 当前批准的默认目标是每个敌方周期 3 HP。可以研究更好的风险表达、软目标及情境调整；如果建议改变原有 3 HP 的含义或默认风险水平，必须标为需要用户确认的产品变更。
- 我此前希望考虑未来 5～7 回合。允许你研究近端精确、远端近似或自适应的规划方式，但要解释如何保留对长期收益的判断；不能只把未来全部删掉。
- 单人模式已有行为需要保留。首个实施方案应能在普通桌面电脑本地运行，优先无需预训练、无需运行时云端大模型。学习方法可作为长期候选，但必须说明数据、训练、部署和冷启动成本。

### 2.1 已经具备的能力

1. 主线程冻结全队状态：身份、生命、格挡、资源、牌堆、能力、遗物、药水、球、怪物和战斗 RNG 等。后台只读冻结根和分支状态。本机玩家不一定是玩家列表第一个。
2. 只展开本机主动动作；队友在后续预测中不主动出牌/用药，但其被动效果、抽牌、受击和回合阶段正常推进。需要队友选择时停止在明确边界。
3. 默认最多推演七个敌方行动周期。额外玩家回合不消耗敌方周期上限；预算不足时允许提前结束，并分别显示实际深度和上限。
4. 采用有界 Beam 搜索，已有动作/选牌展开、模拟 Fork、状态键、转置、并行展开与请求预算。多人禁用原有新颖性组合和多宽度组合，也绕开单人的局外收益与药水反事实审计。
5. 多人已经在原 Beam 宽度内分别保留进攻、防御、铺垫候选。不能把“增加这些通道”当作从未实现的新方案。
6. 每个敌方周期独立统计 3 HP 额度，包含重算前本周期已发生的扣血及自损；治疗、重算、额外玩家回合不刷新额度，未用额度不结转。节点政策账本与战斗状态分开，去重和转置考虑账本差异。
7. 跨请求只保留最多四条路线的纯动作数据，每条至多重新模拟本回合 32 个无选择动作；旧树、旧分数和旧模拟器不复用。重放也计入预算。
8. 战场变化会给旧建议加过期提示，再计算仍由用户手动触发。

### 2.2 当前评分和终局比较

以下是 `0.40.5` 的实现在做什么，不代表我们认定它正确或充分：

- 中间评分大致为：死亡 `-1e12`，胜利 `+1e11`，敌人有效剩余生命每点 `-100`，有上限的格挡每点 `+5`，持续能力价值乘 `20`，另加可达手牌价值与能量等小项。
- 节点另外按各周期超过 3 HP 的累计部分，每点减 `100000`。可见 3 HP 虽称“目标”，超额仍受到很强惩罚。
- 格挡上限目前使用怪物动作中的攻击数值合计。请核对它是否准确表达本机目标、实际来伤和已被其他效果抵消的威胁，不要直接当作已确认 bug。
- 最终比较依次考虑：强制用药要求、本机死亡、窗口完成情况；未完成时优先更深的敌方周期；然后是保命资源消耗、超额扣血、全敌死亡、敌人有效剩余生命、本机累计扣血、存活队友数、胜利回合、药水数量、评分及动作数。
- `EnemyHp` 在这里是引擎计算的有效生命汇总，不等于简单的原始生命总和或已经造成的真实伤害；解释公式前核对它对复活、召唤、离场等情况的定义。

请审视“窗口完整性排在质量前面”“未完成候选优先更深”“每点超额惩罚”“队友生存位置较后”等因素的组合效果，并明确哪些只是静态可疑点、哪些需要失败样本才能成立。

### 2.3 已有证据及其局限

此前 `0.40.5` 的九个局部策略场景覆盖了 1/2/3 HP 换 6 点伤害、4 HP 时防御、低血避死、无来伤攻击、同输出少掉血、立即击杀，以及已付扣血后治疗/重算不重置额度。另有周期边界原生状态对账、七回合合同和单人哨兵。

这些是历史局部证据，不是“真实多人策略已经优秀”的证明。没有真实联机下所有角色、三/四人、操作交错和复杂牌组的完整验收。不要把编译通过、简单双卡案例、单一被动队友模型或完整状态一致性当作决策质量已经达标。

## 3. 先把问题建模准确

请定义状态、观测、本机动作、外部事件、决策时点、目标和计算预算。重点回答：

1. 哪些当前状态在房主和加入方本地确实可读且可信？哪些只是当前代码尝试捕获、尚缺真实网络证据？哪些未来信息不能知道？请做字段级“可观测/可推导/需要核验/未知”表，避免凭空假设队友未来手牌、顺序或意图。
2. 这个问题更适合建模为确定性模拟上的外部策略不确定性、部分可观测决策、随机规划、鲁棒规划，还是它们的局部组合？给出适用条件，不要只给模型名称。
3. 搜索承诺的是一个动作、当前回合动作前缀，还是依赖后续观测的策略？未来尚不可观测的信息不能提前改变当前选择；说明如何避免在不同未来中挑选不兼容的“最优前缀”。
4. 本机结束行动、全队完成玩家阶段、敌人行动、下一回合设置和额外回合应怎样区分？队友行动可能与我交错时，最短可靠承诺边界在哪里？
5. 在相同动作与外部事件序列下，已捕获 RNG 可能让模拟确定；但队友改变行动会改变 RNG 消耗。不要把这个问题简单写成“每回合随机抽样一个伤害”或保证未来牌序始终不变。
6. “队友不主动行动”能提供什么参考？它不是通用最坏情况证明，因为队友行动可能改变目标、共享效果、触发敌方反应或随机流。请解释什么时候仍值得保留这一场景。

## 4. 调研并选择算法

请查阅原始论文、作者资料、官方文档和可核验的开源实现，研究适合当前问题的候选。至少比较以下类别；可合并功能重叠者，也可补充更合适的方法：

| 类别 | 本次需要回答的重点 |
|---|---|
| 改进现有 Beam、best-first 或局部精确枚举 | 是目标错、候选丢失还是预算分配错？修复现有搜索能达到什么程度？ |
| 当前回合强搜索加远期价值评估 | 如何处理牌序、选牌、铺垫、控制和延迟兑现，避免退化成只看当前伤害？ |
| 滚动规划 / Model Predictive Control | 如何与手动重算一致，并缓解不可靠的七回合单一路线？ |
| MCTS / UCT / PUCT 及适用的扩展 | 动作粒度、rollout、先验来源、选择分支与渐进扩展如何设计？无训练先验时是否仍值得做？ |
| 有限情景、鲁棒或风险敏感评估 | 如何在未知真人队友下比较同一个本机前缀？如何防止过度乐观与过度保守？ |
| 有界新颖性、组合搜索、宏动作或分层搜索 | 如何在同一总预算内保留有价值的组合，而非单纯增加节点？ |
| 可选学习方法 | 是否有明确超越无需训练方案的潜力，所需数据与成本是否值得？ |

比较应包含：所需信息、与现有引擎的适配、期望优势的条件、失败模式、计算及内存成本、工程风险和可验证性。不要声称 MCTS、强化学习或更深搜索天然更聪明；不要把合作队友默认建模成最坏情况对手。

请最终明确选择：

- 一个最值得首先实施的主方案，说明为何优于“只调整当前权重”和主要竞争方案。
- 一个成本更低的回退方案及其启用条件。
- 只有证据支持时才给一个长期升级方向，说明什么实验结果会促使切换。

可以得出“算法主体保留，主要重做目标/不确定性/预算分配”的结论，但必须有可证伪的理由。也可以推荐换算法，但必须说明现有基础设施如何复用。

## 5. 主方案必须设计到可以实施

### 5.1 目标函数与风险政策

定义每个量的含义、单位、测量时点和归属。将本机生命、主动自损、治疗、救命资源、队友状态、敌人威胁、实际伤害、支援价值、长期资源、药水成本分开，防止重复计分。

说明哪些是硬约束，哪些是软目标，哪些只用于中间保路，哪些只能在可靠的终局比较。避免用一个未经校准的大总分包办全部职责。

重点解决：

- 3 HP 偏好在高血、低血、确定击杀、消耗战和远期不确定性下如何应用。
- 同输出时减少扣血；同风险时优先有价值输出；免费防御和无收益过量格挡应有不同处理。
- 击杀高威胁目标、减伤控制、铺垫后爆发、队友救援和团队增益怎样获得合理价值。
- 不能只最小化敌方 HP 汇总而忽略威胁分布，也不能通过召唤/复活反复刷伤害分数。
- 不能把估计的队友输出当作本机已经造成的伤害，或让无贡献路线因乐观队友预测获得虚高评价。
- 不同完成深度、未知效果边界、外部选择边界、提前真实胜利和预算截断如何比较，防止“更深但更差”压过“较浅但明显更好的当前动作”。

若使用折扣、CVaR、分位数、约束违约代价或后悔值，写清计算对象与数据来源。情景权重未经校准时，不能输出貌似可靠的胜率或死亡概率。给出初始参数及理由，并标明它们是待调优建议，不是实测最优值。

### 5.2 队友未来与情景生成

明确区分完全不模拟队友主动行为、基于可观测信息的有限合法行为情景、仅在叶子估值中估计队友贡献这几种做法，选择其中必要的最小组合。

如果主方案使用情景：说明情景数量如何随预算变化、如何生成合法动作、如何处理未知手牌和选择、权重从何而来、什么时候因没有可靠信息而降级。考虑队友先动/后动、已经结束回合、进攻/防御倾向及与本机行为的相互影响。

要强调：**同一本机候选在多个情景中评估，和每个情景各自挑一个最优动作再平均，是不同问题。** 给出防止未来信息泄漏和策略混合的机制。

可以研究只依靠本机观察的轻量在线统计，但要说明冷启动、样本不足、队友换人/换打法、条件依赖和统计失效。该方法不能要求真人队友安装软件或发送计划。

精确模拟中的情景必须通过合法动作和唯一引擎推进。若只估计“队友将提供多少伤害/格挡”，只能将其标成近似估值，不能直接改真实分支 HP/资源并冒充原生结算。

### 5.3 时间尺度与搜索组织

比较当前固定七个敌方周期与近端精确、远端近似、按决策相关性自适应分配的方案。解释在哪些场景多看几回合有价值，在哪些场景加深主要放大队友假设误差。

给出候选生成、动作/选牌展开、铺垫保护、重复局面处理、阶段推进、叶子评估、终局排名和 anytime 返回的完整流程。若用宏动作，说明组成、生成成本和不会遗漏关键顺序/选择的适用条件；若用 MCTS，写出选择、扩展、rollout、回传、最终根动作选择和取消规则。

多人现有进攻/防御/铺垫通道已经实现，请研究其有效性和具体缺陷，不要重复添加同名机制。终局评价修好但候选中途已被剪掉，或保路改善而最终排序仍错，都不算完整方案。

滚动规划是用户每次手动请求时重新规划；任何新增自动重算或自动操作建议都必须独立标为产品范围变更。

### 5.4 预算、复用和工程边界

所有候选生成、情景、rollout、旧路线重放、最终验证和失败/取消作业要纳入同一请求成本。分别报告逻辑节点与实际模拟调用，不能通过更换计数单位制造“同预算”收益。说明首条可用建议、质量随时间变化、峰值内存、并行度和过期结果处理。

不得把未改变根上的安全局部缓存扩大成队友已变化后直接复用旧分数。说明哪些可以保留、缓存键包含什么、何时失效，以及如何在新根重放验证。

## 6. 验证设计：证明它真的更会打

先区分三类问题：相同动作的模拟语义错误、对队友未来的模型误差、搜索或排序未找到/未选择好动作。给出定位首个差异的方法；语义不一致应先修模拟。
