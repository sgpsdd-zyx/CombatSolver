日期：2026-09-18。用户在研究归档后明确要求“按照计划对 mod 进行修改”，并延续避免过度工程化的约束。本批从 `db8289e` 开始，采用设计第 12 节允许的低成本回退：完成 F01/F02/F03，保留现役三通道 Beam。代码、测试与本文同批提交到 `codex/multiplayer-advisor`，记入下一版本开发记录；已发布 `0.41.2 / 2dc5d15` 保持冻结，没有新版本、部署或远端发布。

## 已采用的修改

| 发现 | 实现与边界 |
|---|---|
| F01：旧检查点遮蔽真实终局 | `MultiplayerFactsAt` 只对未结束路线读取旧检查点；真实胜利/死亡使用完整结束状态，包括 HP、累计损失、救命、敌方 HP、队伍与药水事实。风险顺序不变，没有把胜利提升到本机死亡、救命消耗或超额之前 |
| F02：本机满血无损胜利提前停止多人搜索 | 原早停条件增加显式单人守卫。多人可继续使用原节点/时间/七周期预算，不能据此承诺结果更快；没有引入新的多人最优性判断 |
| F03：队友根前用药解除本机 Require | 主线程 `BattleDamageTracker.Observe` 在原 `Begin` 窗口内按原生 `PotionUsedEntry.Actor` 统计本机。沿用已有不可变 `BattleDamageSnapshot`，不新增重复根字段，不让 Search 读取实时历史；本机先前已用药仍沿用原豁免规则 |

F03 不重定义自动药水的原生历史分类，不改变逐槽 Force/保护规则，也不让根后自动救命充当显式用药动作。缺少本机身份、药水记录数小于 `Begin` 基线时明确失败；这里没有宣称能识别任意清空后重新增长的历史替换。原始根库存和遗物状态仍由原快照负责。

生产修改只涉及多人事实投影、共享循环的多人守卫和 Runtime 请求计数。没有新增模拟状态、评分维度、缓存、策略开关或预算。原 Pro 回文、抽象脚本、研究期探针及其输出保持原样。

## 本批实际证据

证据根：`.local/mp-pro-implementation-20260918/`；完整命令口径见[测试矩阵](../../TEST_MATRIX.md#多人复审事实与入口修正2026-09-18)。所有请求使用普通 .NET 宿主，单请求外层上限 120 秒，未启动 Godot、Steam 或网络。

- 真实模拟反例：同一根的“空过一周期后两次攻击获胜”与“攻击后结束回合、敌方还剩 4 HP”进入生产最终候选入口。旧 DLL 选择未胜路线，将胜利投影为旧检查点的敌方 10 HP；修正后选择敌方 0 HP 的真胜利。
- 真实搜索循环：相同双卡小局，旧版最后展开第 1 回合、2 个父节点；修正后最后展开第 3 回合、9 个父节点，均未超过原 120 节点预算。观测耗时约 151/161 ms，仅是该固定小局，不代表可见性能或多人策略胜率。
- 原生药水历史：先有一次本机用药再重设 `Begin`，随后队友向本机投药。旧版本机计数为 1，Require 降为 Smart，选中 0 次显式用药；修正后计数为 0，要求保留，实际搜索选中 1 次显式用药。之后本机向队友投药只增加本机计数到 1；已冻结的较早请求不变。Force 与保护控制通过。
- 新增四组生产排序控制：混合池截断仍保住真胜利、两个胜利用完整终局事实比较结束回合、全终局控制、本机死亡优先级。原 R1/R2 的 840 排列、216 三元关系、资格和同池预览/最终选择合同通过。
- 既有多人短搜通过扣血、救援、铺垫、四节点截止、能力隔离、增量等价、原生下一回合和 Fork 合同；七周期哨兵通过六次原生完整状态对账、额外回合、选择、药水和手动操作边界。
- 新运行的单人能力哨兵与已有独立官方 `0e6cc2d` 基线比较 80 项一致、0 差异，含完整路线 JSON、根状态、目标、选择与 RNG；三处多人选路入口均为零进入。总展开 1820、转移 4583、17 动作、2 HP 损失。

早停 fixture 最初误把结果的 `SearchedTurns` 当作实际搜索层数，虽然新代码已展开 9 个节点，断言仍失败。已改为在实际 `Expand` 入口观察父节点回合，并用独立 `stopping` 模式取得失败/通过证据；没有为这个观测修正重跑已经通过的终局和药水用例。初始 fixture 的失败记录保留，不计作生产回归。新的聚合证据明确引用各自原始输出。

## 保留的条件项

| 项目 | 本批处置与继续条件 |
|---|---|
| F04：完成池局部压缩与联合目标 | 暂缓。`Phases` 在 frontier 保路前压缩 completed；最终还可能启用药水回退与预算截止旧层，预览又只接收持有模拟器的候选。仅把 `ended` 拼进局部排序不足以贯通这些集合，还可能提前过滤可展开的无药前缀。后续须先做穿过压缩、预览及最终合池的生产失败 fixture，再在原容量和释放边界内冻结同一实际发布集合；本批没有宣称该问题已修 |
| F05：末父节点的已付卡牌候选 | 暂缓。首次 yield 前已物化的卡批与之后尚未执行的药水/回合尾部不同；完整排空迭代器会继续做新引擎工作，且预算耗尽后的 active 清空仍可能丢掉新增接收结果。需要独立的有界接收及释放证据，不能以删除一个 break 冒充免费修复 |
| F06：共同周期内动作成本 | 暂缓。CP 在下一玩家阶段选择之前捕获，整个子节点的动作数不一定属于 CP；当前没有可直接复用的精确动作游标。末级同分不足以支持新增一套重放/游标状态 |
| F07：根后资源归属观察 | 暂缓。F03 只修根前请求资格，不等于补齐分支救命/药水归属。现有消费入口知道拥有者，但若本批不改变风险政策，新增镜像、Fork、快照、CP 字段只服务尚无消费者的观察；保留为独立小批次，届时验证原生结算和分支隔离。默认全队救命次数及风险次序不变 |
| 旧当前回合预览旁路 | 保留额外待测项。主预览的同池合同通过，不等于证明主预览缺失时的旧回退与最终结果一致；未构造该可见触发过程 |

这些是计划自身的复杂度门槛下的暂缓项，不是阻塞已批准首批的权限问题。没有用资源归属观察暗中改变本机超额、队友死亡与救命资源的优先级；两步挑战、队友情景、隐藏信息政策和新的规划器未实施。
