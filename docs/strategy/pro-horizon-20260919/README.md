## 本地窗口对照

生产基线直接运行六个根、固定 3/5/7/9 周期，共 24 次搜索。统一使用双玩家、本机索引 1、一个敌人、Beam 8、350 节点、3000ms、DOP 1；小预算根仅允许 4 个节点。统计来自正式 `CombatSearchCoordinator` 和实际展开父节点，分别保留窗口上限、展开周期分布、选中路线周期和共同评价周期。

为隔离投资回本时间，根仅给本机 1 能量、一个 `StrikeIronclad` 和一个 `Inflame`，将后者显式加上 Ethereal。这是实验对卡牌的改造，避免“先攻击，下回合再铺垫”混淆当前二选一；不是原版卡牌的默认效果。双方各有 64 层 `BufferPower`，剥离战损差异。七/九周期回本根使用升级攻击和原生力量状态提高放弃当前攻击的成本。

## 原生基础与排序反例

`horizon-native` 单独执行本机 `Inflame`、队友 `Bludgeon` 两个原生手动动作，每步比较完整多人 `ContinuationStamp`，两步均相等。离线宿主用现有同类合同的单调时钟桥接代替 Godot 时钟，仍不启动 Godot、Steam 或网络。它证明这两个非终局动作的模拟基础，不代表九周期完整原生战斗或真实联机验收。现场为 `.local/mp-horizon-20260919/native-r1/`。

`horizon-ordering` 从真实根逐动作回放生成父链：首周期攻击、同一前缀加一个后续防御、同一前缀多过一个周期，以及首周期多打一个防御。四条路线在共同周期 1 的敌方 HP 都为 117。`3ccac17` 比较器同时惩罚后续动作与首周期内额外动作，比较结果均为 -1；共同周期成本方案则预期前两项同分。这个差异不能证明较短或较长后缀的战斗质量更高。实验失败基线见 `.local/mp-horizon-20260919/ordering-before/`。

初版实验分别遇到 JSON 属性名冲突、评估器在胜利后仍追加结束回合，以及原生动作所需 Godot 时钟桥接缺失；均保留失败日志。前两项仅影响测试代码，第三项已由独立原生合同补齐；失败尝试不计为通过证据。

## 研究期实现与验收

本节是 `cb427b5` 的历史证据，生产接入未发布，不能当作 0.41.3 的默认行为。当前 `horizon-ordering` 只在离线宿主内派生共同周期成本，分别断言正式规则和实验方案；完整比较器研究结果仍保留在原提交及下列文件，不用派生值检查冒充新的完整排序政策验收。

生产只修改 `CombatBeamSolver.MultiplayerEvaluation` 的动作数同分项。从现有父链向前定位首次完成共同敌方周期的动作，读取其已有动作计数；不以玩家回合数猜周期，不增加原始检查点字段、状态键、缓存、重放或候选。已释放模拟器的父链仍保留精确数值。若共同周期缺失对应动作边界则明确失败，不退回猜测值。真实胜利/死亡继续比较完整终局，无共同周期继续原后备；后续已知风险仍先于同分项。

修正后后缀牌、后续周期比较都为 0，首周期额外动作仍为 -1。64 组三元关系、模拟器释放后比较和额外玩家回合通过。后者真实回放 Ambergris 的额外回合，确认零敌方周期之后仍把动作成本计入首次实际敌方周期；周期后的防御不影响同分结果。

最终 24 次窗口对照与基线的当前回合动作、展开分布、转移及统一外部评价逐项相同。4 节点根最后保留的后缀多验证一张攻击，终点敌方 HP 为 488，而基线为 494；共同周期仍为 1，当前回合动作和外部结果相同，因此不计为战斗质量提升。数据见 [production-horizon-summary.json](production-horizon-summary.json)。
