## 1. 最终建议与首版边界

建议实现一个 **Co-op Local Advisor**：

```text
多人实机的稳定状态
    ↓ 主线程捕获：本人 + 队友相关状态 + 敌人 + 原生 RNG + 阶段状态
同一个不可变根快照
    ├─ 本人动作搜索：防住再输出
    └─ 本人动作搜索：全力输出
          ↓ 都使用现有卡牌/怪物/状态镜像和跨回合推进
只读路线、下一敌方阶段战损、后续条件预测
          ↓ 任意相关实机变化
旧结果失效 → 从最新稳定状态重新规划
```

两条路线只回答：**在当前战场已经如此、其他玩家此后不再主动出牌/用药的预测条件下，我现在怎样出牌更合适？** 已经存在的队友被动、共享减益、召唤物、伤害转移等仍按已支持的原生语义结算。

首版建议固定以下范围：

| 维度 | 首版推荐 |
| --- | --- |
| 控制对象 | 仅 `LocalContext.GetMe(state)` 对应玩家，不以房主或 `Players[0]` 代替本人 |
| 决策范围 | 本人的合法出牌、本人可决定的选牌、本人合法目标；不枚举队友的出牌组合 |
| 预测范围 | 当前剩余行动阶段，加后续两个正常玩家阶段，默认共看三个敌方结算周期；预算不足时如实显示实际深度 |
| 队友策略 | 不再主动出牌/用药，但正常推进已验证的被动与阶段效果 |
| 输出 | 「防住再输出」「全力输出」两套建议；允许两套结果相同，不为凑差异强造路线 |
| 实机操作 | 仅建议；多人下禁用自动出牌、自动结束回合、开局/回合开始选牌代答 |
| 药水 | 默认不搜索主动用药；保留原生自动触发效果，不能因此删除被动救命机制 |
| 未验证效果 | 显式边界与具体原因，不默认按零效果处理 |
| 不在首版范围 | 联合队伍最优解、预测队友未来手牌策略、自定义网络协议、多人战前 API、全自动托管 |

**最大的必要工作量在「多人阶段推进和怪物目标语义」，其次才是两套搜索目标。** 展示两个按钮本身并不难；若绕过前两项，得到的只是能够在联机时启动、却按单人规则预测的求解器。

## 2. 当前代码给出的基础与限制

### 2.1 已有架构可以继续使用

仓库已经把 Runtime 捕获、Search 求解、模拟分支、只读 UI 与原生部署分开。搜索不是只枚举当前手牌，而是包含回合推进、抽牌、洗牌、持续效果与怪物状态；现有文档明确采用预算限制，而不是以固定回合数保证搜索到整场最优。因此，多人适配应增加**决策条件与目标策略**，不应另外写一套简化伤害模拟器。[S01][S03]

### 2.2 直接影响适配的源码发现

| 编号 | 已确认的位置/符号 | 观察 | 设计后果 |
| --- | --- | --- | --- |
| F01 | `CombatRootSnapshot.Capture` | 主线程捕获；使用 `LocalContext.GetMe(state)`；保留 `PlayerCount`，并创建模拟根 | 保留入口与所有权模型，增加多人上下文，不伪造单人战斗 [S04] |
| F02 | `SimulatedCombatState` 构造与 `MaterializeRoot` | 已捕获玩家列表、多人卡池约束、各玩家遗物/药水等；处理多人缩放模型 | 状态层并非完全从零开始，但不能据此断言多人流程已经正确 [S05] |
| F03 | `CombatPredictionState` | 有按 `Player` 索引的模拟玩家状态表 | 可以继续使用多玩家状态容器，不需要联合动作搜索 [S07] |
| F04 | `SolverController.CanSolve` | 明确拒绝玩家数不为 1 的战斗 | 改为按能力准入，而不是直接删除所有人数判断 [S08] |
| F05 | `BeginCombat`、`ActivateTurnSetupResult`、`MonitorCombatPresence` | 还有单人相关限制，分别影响自动行为、准备结果接收、UI 恢复 | 只开放多人只读建议；自动操作限制应保留 [S08] |
| F06 | `AdvanceRound` | 本人的 `EndTurn` 会进入完整跨回合推进；多处传入 `[_player.Creature]` | 必须把本地结束意愿与全队阶段结算分开 [S09] |
| F07 | `AdvanceRoundPlayerStart` | 围绕本人清格挡、恢复资源、推进玩家开始阶段 | 多人环境中的其他参与者不能永久停在根快照 [S10] |
| F08 | `MonsterMoveSemantics.ApplyForecastMove` | 接收单个 `Creature player`，按此目标执行攻击与部分效果 | 要补充原生多目标/随机目标语义，不能把整个怪物行动按人数重复执行 [S11] |
| F09 | `TargetsFor`、`TargetsForPotion` | 卡牌主要展开 `AnyEnemy`；药水的 `AnyPlayer`/`Self` 路径仍以本人为中心 | 多人合法队友目标需要单独适配，不能全部映射成 `null` [S09][S12] |
| F10 | `FinalPlanOrdering` | 胜利、存活、救命消耗、战略战损、成长、资源等优先于敌方剩余生命 | 只修改最终伤害权重无法实现真正的输出路线 [S13] |
| F11 | `BeamRetentionPolicy`、转置标签、Coordinator | 中途保留与补充搜索同样受原有目标影响；Smart 药水围绕战损与胜利处理 | 两套目标必须贯穿保路、剪枝、提前停止与临时结果 [S14][S15][S18] |
| F12 | `ContinuationStamp` | 本人完整状态、敌方状态、全部生物 Power、九条 RNG 等已参与；未见普通字段逐一覆盖全部队友状态 | 增补队友状态与阶段指纹；不能假设现有 stamp 已覆盖所有联机变化 [S16] |
| F13 | `SimulationSnapshot` / `Snapshot` | 本人死亡与战斗终局分别参与现有结果判定，但单人语义下有合并使用 | 多人需区分「本人不能继续行动」与「整队战败」 [S17][S19] |

**以上是可定位的修改入口，不是全仓库覆盖率报告。** 特别是 `STS2_UNADAPTED_FEATURES_AUDIT.md` 自述为历史版本审计，不应拿其中的覆盖率数字判断当前 `0.40.2` 的能力。[S28]

### 2.3 两个必须避免的误读

**误读一：只求解本人，所以可以把 `Players` 改成只有本人。** 这会改变人数缩放、生成池、目标候选、各方 Hook、死亡条件乃至随机数消耗。源码已经保留这些多人数据，没有理由主动丢掉。[S05]

**误读二：状态容器里有多个玩家，所以只差去掉入口限制。** 当前 `AdvanceRound` 和怪物行动入口仍有明确的单目标、单参与者调用；状态容器具备承载能力不等于阶段调度已经支持多人。[S09][S10][S11]

## 3. 游戏机制：哪些纳入，哪些必须核验

官方当前页面确认在线合作、最多四名玩家以及多人专属卡牌和协同内容；游戏仍在 Early Access，内容与规则持续变化。本文以仓库声明支持的构建为落地基线，不把其他版本攻略中的数值和机制当作 `0.111.0` 的证明。[S24][S25]

### 3.1 建模所需的机制清单

| 机制 | 本次证据与确定性 | 实现原则 |
| --- | --- | --- |
| 多玩家共处同一战场、存在多人缩放和卡池条件 | 官方合作模式说明，加仓库捕获代码 | 直接使用实机当前值与分支中的原生缩放逻辑；不手工除人数或套固定倍率 |
| 玩家方可有多个玩家阶段状态 | 仓库有玩家列表及各玩家回合状态；原生同步细节未实测 | 显式保存每人阶段，不用一个「本人已结束」代表全体已结束 |
| 共同结束玩家方阶段的条件、准备/取消准备的行为 | **需目标版本原生代码和双端回放核验** | 使用阶段适配器；本文不假造确定的 native 方法名或消息格式 |
| 敌人的目标是全体、单个、随机或特殊对象 | 当前镜像以单目标入口处理；每个原生行动的多人目标规则需核验 | 按怪物行动语义解析目标，禁止一概说「所有攻击都打所有人」 |
| 已存在的队友被动与共享效果 | 全体 Hook/Power/遗物状态已有部分基础 | 无主动决策不等于无效果；影响本人或敌人的结算必须保留 |
| 死亡、存活队友、后续复活、战斗胜负 | 现有单人终局实现不能直接证明多人行为 | 原生多人终局为权威；不把本人 HP 归零直接写成团队战败 |
| 随机数受其他玩家行动影响 | 捕获和预测使用多条战斗 RNG 状态；跨参与者具体消耗要审计 | 假设场景内仍可确定回放，但不能承诺队友介入后未来抽牌/目标不变 |
| 其他玩家未装 Mod 的兼容性 | manifest 中 `affects_gameplay: false` 已确认 | 这是元数据，不是联机验收结论；需要连同依赖和补丁一起验证 [S02] |

### 3.2 三个概念必须分开

**动作空间**只包含本人能够决定的动作。这是控制复杂度的主要手段。

**世界状态**仍然包含本人、队友、敌人和影响结果的环境数据。队友当前的格挡、Power、宠物、阶段和死亡状态，不是「额外玩家策略」，只是物理状态。

**未来外部输入**不预测真人队友会怎样操作。首版给它一个公开、可重复的假设：队友没有后续主动出牌/用药；已发生的效果照常存在，自动结算照常发生。

以 `b_i` 表示玩家 i 在一个决策位置的候选数量，联合决策容易引入候选组合及交错顺序；本方案始终只展开 `b_me`。模拟一次动作仍可能遍历多玩家和全体监听器，但这是**状态结算成本的增加**，不是把队友牌序加入组合搜索。实际性能仍须测量，不能承诺固定倍数。

### 3.3 「队友不行动」不是严格保守下界

它通常避免高估队友会帮忙补刀、上虚弱或给格挡，但不保证对所有机制都保守。队友可能触发敌方反应、消耗共享效果、改变随机流；也可能提前击杀目标，使原路线中后续动作失去合法目标。

因此界面应写：

> 条件预测：从当前状态起，未计入队友后续主动出牌/用药；已有被动正常结算。

不要写「必定防住」「最坏情况下也安全」或「队友随便打都成立」。

## 4. 方案选择：为什么选完整状态、单人动作

| 方案 | 改动/复杂度 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 删除人数检查，其他不动 | 表面最小 | 单人回合与目标假设继续存在 | 不可作为正式支持 |
| 复制成单人战斗，按人数分摊敌人 HP | 小 | 杀敌时点、生成、状态、卡池和伤害链全部可能失真 | 不推荐 |
| 当前回合伤害/格挡枚举 | 小到中 | 忽略蓄力、能力、牌序、抽洗牌和未来生存 | 只能用于明确标注的降级预览 |
| 完整多人联合求解 | 很大 | 违背需求；队友安装状态、选择权、行动交错都复杂 | 不做 |
| **完整世界 + 本人动作 + 固定队友环境策略** | **中等，主要集中于语义适配** | 未来是有条件预测，需及时失效重算 | **推荐** |

这不是要复制一个新的多人战斗引擎。建议保持现有引擎为唯一语义来源，只在三个位置增加明确的契约：**谁可以被搜索、如何推进多人阶段、按照什么目标选路线。**

## 5. 两种出牌思路的精确定义

### 5.1 统一比较口径

以下是建议的产品定义，不是当前仓库已有的公式。

设 `H` 为本次比较的正常敌方结算周期数。每条可比较路线都要推进到相同的世界阶段边界；当前回合提前结束不代表已经完成多回合评价。提前真实结束战斗的路线是合法终点；到时限、未知效果或他人选择而中断的路线不是完整 H 周期结果。

为每条路线记录：

| 指标 | 定义 |
| --- | --- |
| `FirstEnemyIncomingHpLoss` | 从当前根到下一次敌方阶段完整结束，本人遭受的敌方/环境结算 HP 损失；不以期末治疗抵消 |
| `SelfPaidHp` | 本人主动支付的生命等成本，单独展示，不能伪装成「零战损」 |
| `MinLocalHp` | 预测期间各已完成结算点的本人最低 HP；有自动救命时另记消耗和濒死事实 |
| `FutureIncomingHpLoss` | 第一敌方周期之后的本人预计受伤，用于展示和同分比较 |
| `EnemyHpDamage` | 实际模拟中敌方真正扣除的 HP；不包含过量伤害、格挡损失和启发式估值 |
| `EnemyProgress` | 相同 H 周期下的有效敌方状态推进，见下节；是排序指标，不等同伤害统计 |
| `HorizonCompleted` | 是否确实模拟到了统一的 H 周期边界 |
| `PredictionCoverage` | 当前结果受哪些已知假设、未支持机制或未完成选择限制 |

不要直接把「当前格挡 − 意图面板伤害」作为防住判断。现有回合末生命周期、怪物行动和状态镜像已经处理实际结算顺序；应通过它们评估减伤、杀敌、控制、反伤、状态等效果。[S11][S21]

### 5.2 输出指标：先用已有敌方状态，不先造复杂归因系统

**首版建议把“打出最高伤害”解释为“在同样预测窗口里，尽可能推进敌方有效生命状态，并优先完成真实胜利”。** 不奖励无意义的过量伤害，也不鼓励为了刷伤害统计而故意延长一场已经能结束的战斗。

最容易落地的主指标是：

```text
EnemyProgress(π, H) = EffectiveEnemyWork(root) − EffectiveEnemyWork(π 在 H 末的状态)
```

优先复用 `StateEvaluation` 里已有的有效敌方生命、存活/复活状态和逐敌耐久信息，而不是重新用手牌文字相加。[S17]

实现时加三条明确规则：

1. 逃跑或无伤移出战场不能直接当作造成了对应 HP 的伤害；保留移出原因/未完成工作账本，或对尚未正确建模的情况停在覆盖边界。
2. 召唤、分裂、形态变化和复活必须通过原有生命周期映射评价。新增敌人意味着剩余战场负担增加；这不等于“本人的伤害为负”。 UI 的伤害值和搜索推进值必须分列。
3. 治疗不能让累计攻击数字无上限地抬高路线评价。终点仍有大量敌方生命的刷伤害路线，不应压过真正击杀或显著降低剩余威胁的路线。

在普通固定敌人遭遇里，这几乎就是复用现有敌方终态指标。复杂遭遇先建立少量针对性的归一化规则和差分用例；**不建议首版构建完整的跨玩家因果伤害归因系统。**

已有共享中毒、反伤或队友被动可能贡献伤害，因此不要把全场预测伤害标成「本人独立贡献」。可选地，从同一根额外做一次“本人也不再主动行动”的基准回放，展示：

```text
本路线相对待命多推进的敌方状态
= EffectiveEnemyWork(待命基准的 H 末)
− EffectiveEnemyWork(本路线的 H 末)
```

基准相同且 H 相同，它不改变候选排序，只改善解释。存在未支持效果时不显示该差值；它仍是条件场景差值，不是现实多人中的精确功劳分配。

### 5.3 模式一：防住再输出

推荐采用**约束式目标**，而不是“格挡与伤害各乘一个大权重”。

首先在完成同一 H 周期的可靠候选中，要求本人能继续存活；默认最低 HP 下限为 1，可另设保留生命阈值。再选择第一敌方周期本人受伤为 0 的候选，最后在这些候选中最大化输出推进与有界的后续潜力。

```text
可行集合：已完成 H 周期；未越过未知语义；本人存活约束满足。
若集合内存在 FirstEnemyIncomingHpLoss = 0：
    只在这些候选中选 EnemyProgress / 长线潜力最好的路线。
否则：
    先最小化 FirstEnemyIncomingHpLoss，再选输出更高的路线。
若没有符合存活约束的候选：
    返回搜索到的较低风险路线，并明确“尚未找到满足生存条件的路线”。
```

后续潜力可复用现有持续效果/资源启发式，但只能作为有界的路线评价或保路依据，不能加进「实际造成伤害」和「确定战损」显示中。

同等输出下优先：未来受伤更少、主动生命代价更低、救命资源消耗更少、动作更少。**没有额外意义的过量格挡不再自动获得优先级。**

这里的“防住”默认指**下一次敌方完整结算**；后续多个周期要求能活下来并展示风险。不要把它暗中升级成“只要找不到整场零损胜利就不输出建议”。

搜索是有预算的。因此即使找不到零损路线，也只能说“当前预算内未找到”，不能声称已经证明“无论怎么出牌都会受伤”。

### 5.4 模式二：全力输出

全力输出去掉第一敌方周期零损的硬约束，允许合理卖血，但仍利用后续抽牌、资源和持续效果最大化多周期推进。

**推荐默认仍要求本人在预测窗口内存活。** 原因是用户要的是多回合输出，而不是牺牲所有后续行动换一个当回合数字；同时可以继续复用大量已有死亡分支处理。

```text
可行集合：同一 H 周期；语义覆盖满足；可见的生存约束满足。
优先：真实战斗胜利。
其次：EnemyProgress；相同推进时比较有界的后续潜力。
再其次：更早消灭威胁、更早兑现输出、消耗更低、生命余量更高。
```

界面必须明确写出默认约束，例如「全力输出 · 要求预测窗口内存活」。**这不是无约束数学意义上的最大伤害。** 若产品决定“全力”必须包含死亡换伤，可另开「允许预测战死」选项；这时不能保留旧的“所有本人死亡候选都先淘汰”的排序，并且必须先完成多人死亡语义适配。

允许战死后也不能虚构死后的本人出牌。对死亡后仍依法存在的中毒、球或共享效果，只有原生规则已核验才能继续模拟；否则结果止于边界、如实显示深度。为降低首版复杂度，建议先不开放该选项。

### 5.5 一个最小数值例子

以下是**人为构造的目标验证样例，不是实际卡牌数值**。本人 30 HP、3 能量；敌方本周期将造成 12 伤害；防御牌每张 6 格挡、攻击牌每张 9 伤害，均 1 费，且本例没有其他效果。

| 出牌方案 | 本周期攻击伤害 | 敌方阶段本人受伤 | 含义 |
| --- | ---: | ---: | --- |
| 两防一攻 | 9 | 0 | 防住模式应优先考虑 |
| 一防两攻 | 18 | 6 | 可以卖血提高输出 |
| 三攻 | 27 | 12 | 在后续生存约束允许时，输出模式应优先考虑 |
| 三防 | 0 | 0 | 没有后续收益时，不应压过两防一攻 |

真正搜索必须继续推进后续状态。若三攻导致下一周期必死，而一防两攻能保住后续大爆发，输出模式不应只因为本周期 27 > 18 就选三攻。


### 5.6 首版比较器可以先用明确的字典序

为避免引入一组难以校准的“伤害/生命/潜力兑换权重”，建议**完成候选**先使用以下排序键，按从左到右比较；此前已筛除覆盖不满足、未完成共同 H、未满足当前生存约束的候选。

```text
防住再输出：
  第一期受伤升序 → 真实胜利优先 → EnemyProgress 降序
  → 后续潜力降序 → 后续受伤升序 → 主动生命成本升序
  → 救命资源消耗升序 → 动作数升序

全力输出：
  真实胜利优先 → EnemyProgress 降序 → 后续潜力降序
  → 更早兑现输出 → 后续受伤/主动生命成本升序
  → 救命资源消耗升序 → 动作数升序
```

后续潜力在这里是**实际推进相同后的决胜项**，而不是未经标定就能抵掉任意 HP 的分数。若以后确需允许“少打一点换 H 之后的大收益”，再用明确的输出容差或经验证的价值函数扩展，不能悄悄混入原先的战损总分。

这不意味着中途 Beam 也机械地套用终点评分：未完成候选仍需按阶段保留能力、资源和控制代表，否则铺垫路线可能在实际收益兑现前被删除。若所有候选都不满足生存约束，应进入明确的风险兜底输出，而非把筛选条件静默取消。

## 6. 如何保留长线能力，而不是退化成一回合贪心

### 6.1 有限时域不等于重写短视求解器

继续复用当前卡牌执行、持续状态、资源、怪物 AI、抽洗牌和跨回合回放；只为多人建议增加一个清晰的**战术评价终点**。达到 H 周期时是成功完成本次条件规划，不是「没有求出整场胜利」的失败。[S03][S19]

建议默认 `H = 3`：当前剩余玩家阶段与后续两个正常玩家阶段，均结算到对应敌方阶段结束。这样能力牌、延迟伤害、下回合资源、牌堆循环可以通过实际模拟体现价值。

额外回合是额外决策窗口，不应草率计作一次正常敌方周期。使用独立的世界周期号、本人回合号与阶段游标；额外回合的多人交互未核验时停在明确边界，不把所有额外回合都压成普通 EndTurn。

### 6.2 避免两种不同深度被错误比较

“已完整预测三个周期”的路线不能与“只走了三张牌、剩余全靠估值”的路线放在同一个最终排行榜。

建议使用共同完成层：先保留双方都已完成的 H=1 结果，再寻找 H=2、H=3 的完整候选；某个目标尚未达到新层时，继续显示该目标的实际深度，而不伪造同深度对比。这是**评价边界的推进**，不是重新引入仓库已经收敛掉的另一套 Short/Deep 搜索框架。

首个 H=1 结果可以先展示，但要写「临时建议，尚未完成后续预测」。未完成 H=2 之前，不应宣称已满足用户所要求的跨回合判断。

### 6.3 保留能铺垫但暂时不打伤害的分支

现有 Beam 保路已经有资源、持续成长、控制、牌堆等路线类型。适配目标时要继续保留这些能力，而不是把“即时伤害最高的几条”作为全部候选。[S14]

例如人为构造两条三周期路线：

```text
直接攻击： 18 + 18 + 18 = 54
先铺能力：  6 + 30 + 30 = 66
```

若都满足生存约束，第二条不应在第一周期因为即时伤害较低而被全局淘汰。排序、保路和候选准入必须一起验证。

### 6.4 远期不确定性的表达

在“队友不主动行动”这一固定场景内，当前 RNG 的分支回放可以是确定的；在真实多人环境里，队友随后的动作可能改变抽牌、目标、怪物条件和共享资源。两件事并不矛盾。

UI 应区分当前步骤和后续假设，不给没有统计模型的预测随意标注“90% 准确率”。可以显示「当前根下精确回放」「受队友后续动作影响」「在某机制处停止」。

## 7. 最关键的改造：多人阶段推进

### 7.1 本人的 EndTurn 不应直接等同于整个敌方阶段

当前 `AdvanceRound` 把本人的回合末、怪物阶段、本人下回合开始连接在一起。多人模式应在同一引擎上增加阶段编排，而不是在 Runtime 伪造别人结束回合的网络动作。[S09][S10]

建议增加只属于模拟分支的阶段账本，例如：

```text
CoOpPhaseLedger（建议新增）
  WorldCycleIndex
  CurrentSide
  每名玩家的 TurnNumber、Phase
  每名玩家已完成的玩家开始/结束子阶段
  队伍结束条件所需的就绪/参与者状态
  本轮敌方阶段是否已经执行
  额外回合状态
  未完成选择的所有者、来源和阶段
```

**实际字段必须从目标构建的原生阶段逻辑反推。** 上述是需要承载的信息，不是在声称游戏内部存在同名 `ReadySet` 或同名网络消息。

模拟行为分为：

```text
本人仍可操作 → 展开本人的出牌与结束意愿
本人不再行动 → 按 NoFurtherActions 假设补齐队友剩余阶段
队伍满足原生阶段转换条件 → 结算一次敌方阶段
进入下一玩家方阶段 → 推进各参与者的必需状态
本人再次可操作 → 继续只展开本人动作
```

这里“补齐”只发生在模拟分支中，不发送任何真实消息，不改变队友的真实回合状态。

### 7.2 不要直接循环调用整个单人 `AdvanceRound`

下面这种改法是错误的：

```csharp
// 错误示意：可能让敌方阶段、共享 Hook、抽牌和全局状态重复发生。
foreach (var player in allPlayers)
    AdvanceWholeSinglePlayerRound(player);
```

即使只循环 `RunPhaseOne` / `RunPhaseTwo` 也不能默认正确：这两个方法同时接受玩家和参与者列表，里面可能存在全局侧回合 Hook。多人实现需要知道哪些步骤按玩家执行、哪些按玩家方执行一次、哪些按生物执行。[S21]

建议把现有逻辑拆成可组合、仍由同一语义实现负责的步骤：

| 步骤范围 | 示例 | 不变量 |
| --- | --- | --- |
| 单玩家 | 手牌收尾、该玩家的资源、该玩家的回合号 | 每个实际参与者每次相应阶段只执行一次 |
| 玩家方整体 | 某些 SideTurn Hook、整体侧切换 | 按原生定义执行一次，不能按人数放大 |
| 单生物 | 对应生物的格挡清除、Power 状态 | 使用正确 owner，并保留原生顺序 |
| 敌方整体 | 敌方开始、行动队列、结束、胜负检查点 | 一个正常世界周期只执行一次 |
| 选择续接 | 玩家开始/结束或效果中的选择 | 所有者与阶段必须保留，不消费他人的选择 |

首个多人根可能已经包含“队友已结束、本人未结束”的混合状态。不能再为队友重复执行已经提交的弃牌、被动、伤害或资源清理；阶段账本要从根状态开始，而不是把每轮都假定为全员刚发完牌。

如果原生允许玩家结束先后顺序影响结果，而未来顺序又没有确定，首版应选一个明确的环境顺序作为**场景参数**，并披露该假设；不能声称自己恢复了唯一真实未来。对会实质影响本人的未验证顺序，直接输出覆盖边界。

### 7.3 队友不主动行动，也必须正常经过未来周期

队友后续不会被搜索，但其状态需要按适用规则推进。例如其格挡是否清除、持续状态是否衰减、自动伤害是否触发、宠物/球是否工作、手牌是否收尾以及是否抽牌，都应由原生语义决定。

不能让队友永远保留根快照中的格挡和持续回合，也不能为了节省性能把其血量钉死。这样的冻结会改变后续目标、被动、转移伤害和存活集合。

这仍然不要求预测队友的意图。自动结算是固定环境过程，不是枚举队友策略。

### 7.4 本人强制结束与额外回合必须走同一入口

不只有 UI 里的 EndTurn 会导致阶段变化。现有搜索中，卡牌请求结束玩家回合也会进入 `AdvanceRound`。多人适配后，这些入口必须经过相同阶段编排，否则普通 EndTurn 正确、特定卡牌仍按单人规则推进。[S09]

额外回合、强制结束、特殊战斗时限是首版高风险集合。支持条件应按具体原生机制验证；没有验证的分支标记为未支持，不把它们静默当普通回合处理。

## 8. 怪物行动与队友目标：另一个不可省的核心

### 8.1 当前攻击预测结构还不够表达多人目标

`ForecastMove` 主要记录怪物、行动和攻击次数/基础伤害；`MonsterMoveSemantics` 以一个玩家生物为接收对象。`IntentForecaster` 读取意图时会使用玩家生物集合，但这并不意味着后续伤害已经按多人目标正确结算。[S11][S20]

建议为经过验证的怪物行动增加目标计划，例如 `PredictedTargetPlan`，至少能表达：

```text
目标类型：全体有效玩家 / 特定玩家 / 随机玩家 / 特殊目标规则
目标选取时点：行动开始 / 每次命中前 / 原生另定时点
目标顺序：按原生名单顺序或原生确定的顺序
随机选择：使用对应分支 RNG，禁止额外读取实机 RNG
```

这些分类是设计要求，不是对所有怪物的统一规则。具体行动仍由已有怪物镜像或小型适配描述器提供语义。

### 8.2 不要对每名玩家重复完整怪物行动

错误方式：

```csharp
// 错误示意：会重复增益、召唤、行动后效果，且可能改变反伤顺序。
foreach (var player in players)
    MonsterMoveSemantics.ApplyForecastMove(..., player.Creature, ...);
```

正确方向是把“一次怪物行动”与“这次行动中的命中目标”分开：

```text
行动前效果：按原生规则执行
建立一次攻击上下文
    遍历原生定义的命中序列
        在正确时点确定目标集合
        按正确顺序对目标结算命中与转移
        处理每次命中依法触发的死亡/反应/选择
结束本次攻击上下文
行动后效果：按原生规则执行
在原生安全点检查真正的战斗终局
```

既不能把怪物伤害按人数均分，也不能把显示意图伤害盲目乘人数。本人应受到多少伤害，最终由其真实被选中情况、格挡、Power、宠物和伤害重定向共同决定。

### 8.3 为什么连队友受伤也可能影响本人

一个简单的机制类型例子：同一次多目标行动先命中队友，队友的反伤使怪物死亡；该行动是否还会继续命中本人，取决于原生攻击命令的精确规则。只算本人这一份伤害可能错误地判定本人会受伤；随意提前终止又可能错误地判定安全。

这是必须做原生差分的理由，不是要求求解队友的牌。类似地，队友承伤、伤害转移、被动治疗和死亡后效果都属于世界结算。

### 8.4 本人的合法队友目标不等于求解队友

本人的卡或药水若原生允许指定队友，枚举这些合法目标只增加本人的少量候选，不会变成多人联合求解。

需要统一修改候选生成、计划序列化、回放和显示，不能只在 `TargetsFor` 多返回几个对象。建议目标身份使用：

```text
TargetKind + StableCombatId + 必要时的 PlayerNetId
```

保留旧的敌方索引只是显示兼容，不能用列表下标作为跨状态复用依据。目标类别和字段名可按现有 `PlanAction` 兼容实现，但语义必须明确。[S09][S19]

动态目标类型继续通过已有 `CombatPredictionSimulator.GetTargetType` 等分支语义解析，不从原始卡面硬编码。[S12]

涉及“由队友选择一张牌”等真正的他人决策时，不能由本地求解器替对方选。应停在 `ExternalPlayerChoice` 一类新增边界；只有效果全部自动、无需其他玩家输入且已有镜像时，才继续预测。

## 9. 根快照、指纹与分支所有权

### 9.1 复用现有根，不另建有损副本

保留 `CombatRootSnapshot.Capture` 的主线程捕获、捕获前后状态一致性检查、物化根和 `ForkSimulator`。新增多人字段应成为该根或其不可变附属上下文，而不是让 Worker 随时去查询 `CombatManager`、`RunManager` 或队友实机对象。[S04][S05]

`Player`、`Creature` 作为稳定身份引用可以继续存在；但任何会变化的 HP、牌堆、遗物状态、阶段、Power 等值必须来自根或分支。不能因为一个 helper 收到了 `Player` 就直接读 `player.Relics` 或真实 `PlayerCombatState`。

### 9.2 建议增加多人上下文指纹

当前 `ContinuationStamp` 已经相当严格，但其普通玩家字段以本人为主；全部生物 Power 已纳入，并不能替代队友的普通状态字段。[S16]

首版建议采用保守的完整相关状态校验，至少覆盖：

| 类别 | 多人额外校验内容 |
| --- | --- |
| 身份与名册 | 本人 NetId、全体参与者与顺序、战斗实例、敌人/宠物身份、存活与移出原因 |
| 阶段 | 每名玩家回合号和阶段、已提交的阶段步骤、全队转换条件、待处理选择所有者 |
| 数值 | 所有可能受本地动作/被动影响的玩家 HP、格挡、资源与状态 |
| 效果 | 相关遗物实例状态、Power 的来源/目标关系、球/宠物、共享触发计数 |
| 牌与随机 | 原生客户端已持有且参与预测的牌堆与卡牌状态；现有完整 RNG 状态 |
| 配置 | 目标模式、H、队友环境策略、药水规则、覆盖能力版本 |

不要通过新协议索取原生客户端没有的数据。若某个自动效果依赖当前客户端缺失的信息，应标记覆盖边界，而不是编造队友手牌。

后续可以根据严格证明的依赖关系减少失效范围；首版不建议一开始就做复杂的最小依赖缓存。

### 9.3 不能弱化原有随机数一致性

现有代码要求九条 RNG 的完整内部状态进入语义比较，而不只是计数器。多人也应遵守。不要为了让缓存“更容易命中”而忽略队友随机操作造成的 RNG 差异。[S16][S23]

可以另建轻量的 UI 变化标识判断是否需要刷新文字，但它不能代替真实路线的可复用性判断。

### 9.4 新增字段必须正确 Fork

多人阶段账本、目标计划游标、队友状态、统计账本等只要会在分支内变化，都要按现有 Fork/写时复制机制拥有独立可变状态。必须测试：修改一条路线中队友的格挡或 Power，不会影响实机、根、兄弟分支及另一种目标的搜索。[S06][S29]

正在结算的卡牌、选择或死亡事务不能被随意当作稳定 Fork 点。沿用当前检查点与续接机制，并扩充所有者/阶段上下文，而不是捕获“半个联机动作”的快照。

## 10. 搜索层如何改：不是只换最后一行分数

### 10.1 保持一个模拟器，显式注入目标策略

建议在 `SearchPolicySnapshot` 增加模式和多人规划选项。默认 `Solo` 必须保持当前行为，避免影响已经成熟的单人使用场景。

下面是**接口形状示意，不是可直接编译的补丁**：

```csharp
internal enum PlanningObjective
{
    Solo,
    CoOpDefendThenDamage,
    CoOpMaxDamage
}

internal sealed record CoOpPlanningOptions(
    ulong LocalPlayerNetId,
    int HorizonEnemyCycles,
    int MinimumLocalHp,
    bool AllowPredictedLocalDeath,
    string TeammatePolicyId,
    string CoverageVersion);

// 保路和最终排序仍是两个不同职责，不能强行混成同一个总分。
internal interface IPlanningObjectivePolicy
{
    RetentionFacts EvaluateRetention(in CandidateFacts candidate);
    int CompareCompleted(in CandidateFacts left, in CandidateFacts right);
    bool IsUsableEndpoint(in CandidateFacts candidate);
    bool CanProveNoBetterResult(in SearchFacts search);
}
```

尽量复用现有只读事实投影与 policy snapshot；不一定要新增上述完全同名接口。核心要求是**目标成为不可变输入，所有目标相关逻辑都从同一契约派生**。

### 10.2 需要一起接入目标的地方

| 层次 | 适配要求 |
| --- | --- |
| `StateEvaluation` | 输出多人阶段与战术指标；区分本人存活、团队终局、H 完成与未知边界 |
| 动作候选筛选 | 输出模式不能只保留旧策略偏爱的生命/格挡候选；保留铺垫与资源代表 |
| `BeamRetentionPolicy` | 分别为两个目标排名、保留必要分支；维持既有牌序/选择多样性机制 |
| `FinalPlanOrdering` | 对多人完成窗口使用第 5 节目标，不再把“没单独打完整场”放在错误等级 |
| 临时结果与最终结果 | 用相同的完成候选比较合同，不让预览和最终选择互相打架 |
| `CombatSearchCoordinator` | 识别战术窗口完成；禁用不适用的整场战损达标早停及失败恢复条件 |
| 转置/支配标签 | 纳入新目标有关的路径统计、阶段与剩余时域；不同目标不共享错误支配关系 |
| 路线缓存 | 将 mode、H、场景条件与多人指纹加入身份，不复用另一种目标的结果 |

当前 Coordinator 的 Smart 药水、可接受战损判断与补充搜索有明确的单人目标语义；首版直接为多人构造不主动用药的局部 policy，比试图一次改好全部药水梯度更容易隔离验证。[S15]

### 10.3 两套搜索如何组织最省事

**推荐首版两次独立搜索，共享同一个不可变根；各自持有独立 `SearchRunContext`、转置表、候选池和结果。** 不要共享可变树，也不要认为从同一棵旧战损树的结果里挑两条就等价于两个目标。

为避免实现复杂的可暂停搜索，可以先串行运行两次预算内搜索：先给防御目标一份小预算，再给输出目标一份；后续是否追加搜索由同一请求的剩余预算决定。若采用现有并行展开，两次请求也必须共享整体 CPU/内存上限，不能让每次都独占最大并行度与 NoGC 区域。

后续有性能证据后，再考虑同根下的双目标候选共享。那是优化项，不是首版前提。

### 10.4 早停不能沿用“零损胜利已足够”的结论

找到一条零受伤路线，只证明它满足防御约束，不证明它已经是在这些路线中输出最高的。输出模式也不能因为找到一条“可接受战损”路线就停止改善输出。

首版的简单规则是：在达到预算或没有可继续搜索的候选时结束；只有对**当前目标**成立的上界/下界证明才允许提前声称无法改善。现有只针对单人主目标的证明不能直接搬过来。

### 10.5 支配剪枝尤其容易偷偷抹掉输出路线

两个分支即使到达相同可变战场状态，也可能有不同的“第一敌方周期受伤”“主动卖血”“已使用救命资源”“早期输出”和时域位置。它们在新目标下未必等价。

首版建议保持保守：只对同目标、同环境策略、同阶段、同剩余 H、同完整语义状态，且目标相关路径标签确实可比较的候选进行支配。暂时无法证明的新增维度宁可少剪枝，不要用旧 HP 标签默认为安全。[S18]

特别注意：当前时点“现在结束会死”的待命评估，不代表所有后续动作都救不回来；一张控制、斩杀或防御牌可能改变结论。待命结果可指导保路，不能无证明地成为提前砍掉整个父节点的下界。

### 10.6 战术完成与失败必须分开

建议在结果层引入以下含义，可用新增 enum 或现有类型扩展表达：

```text
HorizonCompleted        正常完成本次条件规划
CombatCompleted        原生意义的战斗结束
BudgetLimitedPreview   有部分建议，但未完成目标窗口
ExternalPlayerChoice   需要其他玩家决策
UnsupportedSemantics   缺少多人目标/阶段/效果支持
StaleRoot              实机条件已经变化
```

现有 `SearchBoundaryReason` 的 `TimeLimit`、`NodeLimit`、`PendingChoice` 等仍保留其原义；不要把新完成状态塞进 `TurnLimit` 后又被上层当成搜索失败。[S19]

## 11. 统计实现：不要只改显示数字

### 11.1 区分实战既有战损与本次预测增量

每次多人重算都从最新根开始。显示“本路线预计受伤”时，必须是根之后的增量，不能把本场已经发生的伤害在每次重算后重新计入。原有整场 `BattleDamageSnapshot` 可以继续用于单人或整场说明，但多人战术指标应有明确的 root baseline。

### 11.2 用标量累计，最终路线再生成解释

当前引擎已有伤害来源上下文和可选的动作/遗物触发记录，适合复用解释基础；但不能假设所有生命变化路径都已被最终展示记录覆盖。[S26]

建议新增轻量分支账本，平时只保存累计值、必要的小型逐敌信息和阶段归属；最后对两条选中路线重放，生成详细的伤害/受伤解释。不要给每个搜索节点存一份完整事件列表。

至少审计普通伤害、直接 HP 修改、斩杀、治疗、生命成本、反伤、伤害转移、宠物代伤、死亡与自动救命的所有写入路径。分类不确定的损血不能被默认归为“可忽略的主动成本”，更不能据此标记防住。

### 11.3 不混用三类数值

```text
实际 HP 伤害：分支中真正发生的 HP 扣除。
敌方有效状态推进：给搜索排序使用的终态变化。
远期潜力：启发式估值，尚未实际发生。
```

例如一张能力牌当前造成 0 伤害、未来有价值，应该通过保路和后续回放获得评价，不应该在当前伤害显示里直接加一个“预计价值 30”。同理，给队友力量但不预测队友未来主动攻击时，不应凭空折算几十点队友输出。

## 12. 实时变化：失效、重算和防止计算饥饿

### 12.1 只在原生动作完成的稳定边界抓根

网络消息到达不等于动作已经完成。事件钩子应放在原生动作提交完成、阶段/选择落定的安全位置；具体挂钩方法需在目标程序集里定位。

无需等待全队结束回合才提供建议，否则本人最需要建议时反而不能算。但也不能在其他玩家卡牌尚未结算、正在选择或真实队列尚有未完成语义时把中间态包装成稳定根。

### 12.2 使用已有 Session / generation 模型

沿用 `SolverControllerSessions` 与当前搜索 generation 的所有权方式，不新增一套互不相干的全局任务状态。[S22]

建议结果身份至少包含：

```text
CombatInstanceId
RootGeneration / WorldRevision
LocalPlayerNetId
Objective
Horizon / TeammatePolicyId
PolicyFingerprint / CoverageVersion
```

发布前在主线程确认身份仍匹配。旧 Worker 即使晚返回，也只能释放自己持有的资源，不能覆盖新一代结果。

### 12.3 推荐的刷新状态机

```text
相关实机变化发生
  → 立即把两套旧建议标为过期，禁用任何执行入口
  → 取消旧搜索，只保留一个“最新待计算状态”标记
  → 等原生动作完成并经过短暂合并窗口
  → 主线程重新捕获完整根
  → 对新一代状态分别搜索两个目标
  → 只接收同代结果
```

首版可把事件合并窗口设为约 100–200 ms 作为**待测配置起点**，不是性能保证；UI 结果更新可复用当前约 200 ms 的预览节流思路。[S03]

关键是**先标记失效，再等待合并**。不能因为延迟重算，就把旧路线继续显示成可依赖的当前建议。

### 12.4 连续出牌时的可用性

只保留一个活动请求和一个最新待计算标记，避免每张牌都排出一条后台任务。取消需要按现有并行 worker 排空/资源释放合同完成，不能遗留分支。[S03]

持续变化时，应显示「队友持续行动，等待稳定状态」，而不是让进度条永远假装即将完成。可以保留旧路线供观察，但须显著标记旧状态、不得作当前推荐。

**不应为了计算而暂停整场网络战斗，或自动锁住其他玩家输入。** 在实际配合中，玩家可以自然选择等队友动作落定后再参考建议；Mod 只对稳定根提供服务。

### 12.5 本人按建议操作后的复用

首版最简单的策略是：任何相关提交后重算。性能允许时，可先对本人的已执行前缀做完整多人 stamp 核对，精确一致才沿用后缀。

一旦队友介入，不能仅因目标还活着、本人手牌看似没变就继续沿用。中毒、易伤、遗物计数、阶段和 RNG 等变化都可能影响剩余路线。[S16]

## 13. 药水、协同卡和未支持效果的边界

### 13.1 药水先限制主动决策，不删除原生效果

首版两个目标统一使用「不主动用药」，并在 UI 显示。默认策略必须是本次多人请求的局部覆盖，不能把用户保存的单人药水策略改掉。

特别注意 `PotionStrategy` 里可能有强制使用指令；只改一个 `PotionPolicy.Disabled` 未必足以消除所有上层约束。应为多人构造一致的只读策略快照，明确是否忽略主动用药指令；不能仍报“强制药水未满足”而拒绝一条正常战术路线。[S15][S31]

自动触发的救命药水或其他被动仍是世界语义的一部分。统计中要显示预计消耗，不得把“禁止主动用药”解释成“假定这些物品不存在”。

后续开放主动用药时，仍只枚举本人的药水和原生合法目标。输出模式不能继续用“至少节省若干 HP”作为伤害药水的唯一准入标准；应按新的输出目标处理，同时尊重用户逐瓶保护。

### 13.2 多人专属卡的支持应按效果分类

| 效果类型 | 首版处理 |
| --- | --- |
| 本人独立攻击/防御/资源/能力，现有镜像可在多人根上正确工作 | 纳入 |
| 本人指定一个队友，效果全部自动且已验证 | 枚举合法队友目标后纳入 |
| 修改共享敌人状态 | 保留真实效果，队友之后介入再重算 |
| 仅增强队友未来主动出牌 | 可以保留合法动作，但不虚构队友未来出牌收益；可能低估这类协同 |
| 触发队友必须选择/确认 | 停在他人选择边界，不替对方做决定 |
| 依赖客户端缺失的信息 | 停在数据覆盖边界 |
| 额外回合/全队阶段改变，尚未验证 | 标记特定机制未支持 |
| 第三方 Mod 新增战斗语义，未有可靠镜像 | 使用现有未支持诊断，不当成无效果 |

多人专属卡的存在由官方确认，但每张卡是否被当前镜像覆盖，应通过项目覆盖目录与真实用例核验，不能从卡牌名字或单人成功案例推断。[S24][S29]

### 13.3 未知要分级，不能一概吞掉

**已知不支持的分支**可以拒绝扩展，同时明确显示“未评估该类动作”，继续搜索其他可验证动作；此时结果只是在受限动作集合中推荐，不是所有合法路线的最优。

**基础环境就含有未建模被动**时，其他路线也会受影响，不能靠跳过一张卡解决。应停止可靠跨回合建议，返回具体原因和已完成的预测范围。

**意外异常**继续按项目现有规则暴露错误、保存证据。不能 `catch` 后继续按零伤害、无 Power 或“视为安全”处理。[S03][S29]

## 14. 「只有本人装 Mod」如何落实

### 14.1 架构上不需要其他人安装求解器

本方案不交换私人搜索树、不给队友分发策略、不要求队友运行相同算法。只读建议使用当前客户端原本就拥有的战场状态；真人仍通过正常游戏界面出牌。

因此，**求解架构可以设计成单端辅助**。但游戏是否允许当前 Mod 与依赖在非对称安装情况下正常联机，是独立的兼容性问题，必须实际验证。

### 14.2 不能只依据 `affects_gameplay: false` 下结论

仓库 manifest 确实声明 `affects_gameplay: false`，并依赖 RitsuLib；同时 `Entry` 注册的不只有 UI，还包含多类运行时补丁。必须检查这些补丁对原生战斗、模型、速度、输入、随机数和网络确定性的作用域。[S02][S27]

建议按以下原则审计：

| 补丁/能力 | 多人建议模式原则 |
| --- | --- |
| 纯 UI、日志、搜索 Worker 内隔离逻辑 | 在确认无真实状态副作用后允许 |
| 模型克隆、镜像隔离、原生缓存相关补丁 | 逐项确认只读/隔离边界和原生等价性，不能只凭名称放行 |
| 自动出牌、自动结束、原生选择代答 | 首版多人禁用 |
| 加速、跳动画、全局流程优化 | 没有多人确定性验证前保持关闭或单人门禁 |
| 数据上报、问题包 | 不因多人快照而扩大自动上传内容；队友标识和牌堆等默认脱敏 |

如果原生联机握手或某个必要依赖确实要求双方安装相同内容，应如实报告限制，再考虑拆分更小的只读辅助模块。**不要通过伪报 manifest、隐藏依赖或绕过原生一致性检查来宣称兼容。**

### 14.3 最小联机验证矩阵

至少验证四种安装组合：房主装而客机不装、客机装而房主不装、双方都装、双方都不装作为对照。必须把 RitsuLib 的实际安装组合一并记入结果。

两人通过后再覆盖三人、四人；确认加入、战斗、不同结束顺序、断线重连和跨战斗状态恢复。不仅检查“能进房间”，还要检查是否产生不同步、额外原生动作和不应有的消息。

首版“仅建议”的重要收益是：即便用户操作与推荐不同，也不会由求解器直接干预联机流程。但只读模式并不自动证明所有全局补丁都无害。

## 15. UI 应怎样让两种思路真正有用

### 15.1 两张卡片，共同条件可见

下面是**界面文案示意，数值均为虚构示例**：

```text
多人 · 仅规划本人 · 状态 #184
条件：队友后续不主动出牌/用药；已有被动正常结算
药水：不主动使用    预测：3 个敌方周期    本人：条件预测中存活

[防住再输出]
下一敌方阶段受伤：0     主动生命成本：0
本周期敌方 HP 伤害：18  三周期敌方 HP 伤害：64
顺序：能力牌 → 防御牌 → 攻击牌（目标 A）
后续：下一周期进入资源/伤害收益；未来受伤另列

[全力输出]
下一敌方阶段受伤：7     主动生命成本：0
本周期敌方 HP 伤害：31  三周期敌方 HP 伤害：82
顺序：攻击牌（目标 B）→ 过牌 → 攻击牌（目标 A）
提示：比防御路线少保留 7 HP，换取更高的条件预测输出

[重新计算]  [停止本次计算]
本版本多人模式不提供自动执行。
```

若无法可靠归因，伤害栏改成「本路线预测敌方减血，含现有被动」，不能继续显示“本人造成”。两条路线不同 H 时，禁止直接显示这种三周期差值比较。

### 15.2 几种必须有的状态文案

| 状态 | 建议文案 |
| --- | --- |
| 找到零受伤候选 | 在当前条件预测下，下一敌方阶段不掉血 |
| 没找到零受伤候选 | 当前预算内未找到零受伤路线；所选路线预计受伤 X |
| 没找到生存候选 | 当前预测窗口内未找到满足生存条件的路线 |
| 队友刚行动 | 战场已变化，原建议已过期 |
| 只完成一周期 | 临时建议：仅完成下一敌方阶段预测 |
| 遇到队友选择 | 后续需要队友选择，预测止于此处 |
| 仅支持部分动作 | 部分多人效果尚未评估；推荐范围受限 |
| 两个目标选中同一路线 | 当前状态下两种目标得到相同建议 |

不要把“当前预算内最佳”“当前假设下有效”省略成“必定最优”。

### 15.3 跨回合路线展示与未来自动执行解耦

可以继续展示第 2、3 周期的计划和选牌解释，但它们应默认折叠并标明条件预测。当前可参考的动作集中在本人的当前操作阶段。

未来考虑半自动时，优先一次只提交一个本人动作，提交前重核完整状态、目标、所有者与合法性；通过原生入口而不是直接修改战斗。即便如此仍需应对检查后、真实执行前被队友动作插入的竞争，最终以原生合法性与提交结果为准。

首版不要承诺“自动打一整回合”；更不能把模拟环境里补齐的队友 EndTurn 转成真实网络输入。

### 16.1 三个可以显著减少工作量的现有入口

**第一，复用现有策略开关。** `SearchPolicySnapshot` 已有 `IgnoreLongTermRewards`、`StopAtAcceptableBattleHpLoss`、`IncludeTurnSetup` 等。多人可局部设为不追求局外成长、不按整场战损达标早停、不接管 turn setup；这些控制不要全部重新造。[S31]

还应检查遗物目标列表、强制药水指令及 portfolio/novelty 的补充预算。首版可以在多人局部策略中关闭未完成目标适配的补充搜索，保留主 Beam；单人配置不变。

**第二，利用已有原生全状态序列化。** `SolvedRouteCache.Capture` 已使用 `NetFullCombatState.FromRun`，还追加各玩家牌组序列化；这为多人根身份和差分证据提供了可复用入口。[S32]

可以把这部分提取成主线程的只读原生快照构件，再附加 Mod 镜像与多人阶段信息，而不是从零写一套全字段 JSON。须核验原生序列化是否覆盖所需阶段/选择状态；现有持久缓存为了重载会清除部分选择/奖励序列计数，**不要不加区分地照搬这种归一化到实时并发校验**。

**第三，保留完整状态与现有镜像。** 当前 `SimulatedCombatState` 已为各玩家相关数据做根物化。应首先证明其在多人根下的隔离能力，再补阶段编排；不是重新复制所有卡牌效果。[S05][S07]

### 16.2 新模块建议保持少而明确

推荐最多先增加四个主要职责：

```text
CoOpPlanningContext       不可变条件：本人、时域、环境假设、版本
CoOpRoundAdapter          原生语义下的多人被动阶段编排
CoOpObjectivePolicy       两种目标的评价合同
CoOpTacticsResult         共同根下的两套结果与有效性信息
```

阶段账本、目标计划和指标可以作为上述模块的内部类型；不需要为每个状态建一个新服务。单人仍走现有路径；有验证后再逐步共享适当底层函数。

## 17. 分阶段实现路线

以下是依赖顺序与相对风险，不是工期承诺。

### 阶段 A：先证明可捕获、可隔离、可非对称联机

固定 commit、游戏程序集版本和依赖；用最小双人战斗验证原生加入与战斗同步，记录稳定阶段轨迹。只对原生已经提交的状态抓根，验证 Fork 修改本人和队友均不触及实机。

交付物应包括：版本清单、原生阶段/目标说明、至少一个双人快照、根与分支隔离断言、安装组合结果。这个阶段可以不输出路线，避免 UI 掩盖语义问题。

**通过门槛：** 已确认最小只读 Mod 能正常联机；真实双方状态不被模拟改变；可识别本人和稳定捕获点。

### 阶段 B：打通最小多人跨回合语义

从普通攻击、防御、一个已验证怪物的场景开始，队友不主动行动。适配多人结束/开始阶段、多目标攻击、本人/团队终局，连续核验至少两个正常敌方周期。

先不加协同选牌、不用主动药水、不支持未经验证的额外回合。遇到这些机制明确退出可靠预测。

**通过门槛：** 对同一根和同一动作序列，模拟与原生阶段末状态一致；所有已结束参与者都不重复触发；敌方阶段不按人数重复。

### 阶段 C：接入两套目标与战术时域

加入第 5 节指标、共同完成边界、两次独立搜索、目标相关保路与支配。复用已有策略开关，先关闭多人下未适配的整场补充搜索与持久缓存。

**通过门槛：** 简单目标样例正确；铺垫路线可跨回合胜出；H 完成不被上层当失败；两种目标不会被旧排序统一拉回最低战损路线。

### 阶段 D：做实战可用的刷新与展示

接入原生提交后的失效通知、合并重算、代际结果校验；添加双卡片、实际深度、条件说明和覆盖边界。不同玩家持续操作时不堆积请求、不错误发布旧结果。

**通过门槛：** 真实双端联机中旧结果不可冒充新状态；无自动队友输入；没有 UI/全局补丁引起的不同步。

### 阶段 E：扩展覆盖与性能

逐类加入队友目标卡、复杂怪物、三四人场景、更多被动与必要的阶段特殊情况。收集性能分布，再决定是否启用更多搜索组合、持久缓存和更深的 H。

**正式首版至少应有一组普通战斗完成 H≥2 的原生多人验证。** 只有当前回合枚举通过，不应宣称已经完成本需求的跨回合多人适配。

半自动执行、允许战死输出、队友策略采样、多目标共享搜索树都放在后续独立阶段，不与基础语义适配捆绑。

### 18.2 两套目标与搜索行为

| 测试 | 核心断言 |
| --- | --- |
| O01 | 可零损时，防御路线不为更高即时伤害放弃已找到的零损约束 |
| O02 | 相同安全性下，足够防御加攻击优于无收益的过量格挡 |
| O03 | 输出模式允许非致死受伤换取更高多周期推进 |
| O04 | 第一期伤害低、后续收益高的能力/资源路线能被保留并胜出 |
| O05 | 先杀敌/施加控制也能被识别为防住，不限定必须打格挡牌 |
| O06 | 治疗不能抹掉已经发生的受伤；主动生命成本单独显示 |
| O07 | 过量伤害不计入实际 HP 伤害；启发式潜力不混入伤害数字 |
| O08 | 两目标相同结果可以正常显示，不人为强制不同首牌 |
| O09 | H=1 和 H=3 候选不被当作同样完成程度比较 |
| O10 | 到 H 的正常终点不触发“未胜利则无限继续补搜”的流程 |
| O11 | 修改目标会改变中间保路，而不只是最终结果重排 |
| O12 | 转置标签不同的关键受伤/资源路径不会被错误合并 |
| O13 | 多人默认不主动用药，但被动救命仍依法结算并计数 |
| O14 | 多人策略覆盖不污染用户保存的单人设置 |

### 18.3 并发、UI 与联机兼容

| 测试 | 核心断言 |
| --- | --- |
| R01 | 队友只增加自身格挡、敌人 HP 未变，仍能正确识别相关状态变化 |
| R02 | 队友抽牌/随机行动只改变 RNG，旧后续路线也不能错误复用 |
| R03 | 一次动作多事件通知被合并，但旧建议立即失效 |
| R04 | 旧搜索晚于新搜索完成，不得覆盖新结果 |
| R05 | 敌人被队友击杀后，旧目标动作不继续作为当前建议 |
| R06 | 持续操作与反复取消不会堆积任务、泄漏分支或阻塞主线程 |
| R07 | 结束战斗/进入新战斗/重连后，旧根全部无效 |
| R08 | 房主单端装、客机单端装、双方装、都不装对照均记录结果 |
| R09 | 三四人验证不出现按人数重复的原生动作或同步差异 |
| R10 | 多人 UI 没有任何通向自动执行、队友结束或选择代答的遗漏入口 |

### 18.4 复用项目现有测试层级，但不能把离线测试当联机证明

项目现有契约要求构建/边界检查、最小差分、Fork/跨回合和完整场景等分层验证；也明确离线宿主不替代游戏内正确性验收。[S03][S29]

建议对应使用：

- **L0：** 原有构建、结构边界、序列化和比较器合同测试。
- **L1：** 最小卡牌、怪物命中、Hook、HP 统计的原生/模拟差分。
- **L2：** 多人分支隔离、混合阶段根、完整跨周期回放与增量/完整回放一致性。
- **L3：** 真正双端/多端联机、非对称安装、持续出牌、UI 与帧时间验证。

现有无人测试与原生重放文档包含单人路径，不能未经扩展就声称它们能验证真实多人网络过程。扩展 `ScenarioBuilder` 的多玩家模拟 fixture 可以验证状态语义；真实多人握手和同步还要独立测试。

本文没有执行上述测试，不把设计的测试名称当作现有已通过用例。

## 19. 性能与风险控制

### 19.1 先测哪些指标

| 指标 | 用途 |
| --- | --- |
| 主线程根捕获耗时与分布 | 防止多玩家牌堆/序列化导致帧卡顿 |
| 每次分支推进、每周期结算成本 | 区分状态体积与搜索分支数的问题 |
| 两种目标分别的有效 H、节点、耗时 | 防止一条有深度、另一条长期只是临时建议 |
| 取消到排空耗时、未释放分支数 | 防止队友持续行动时资源积压 |
| 结果发布时的根年龄、过期比例 | 判断建议是否赶得上实战节奏 |
| 主线程帧时间、进程内存、GC 暂停 | 不能只优化 Worker 总吞吐 |
| 原生/模拟差异率及具体首个差异 | 正确性优先于更大的节点数 |

合并窗口、H、Beam 宽度和预算都应是可调参数。**不要把单人长时间预算直接乘二投入多人实时重算，也不要提前宣称“几百毫秒一定算完”。**

### 19.2 首版风险排序

| 风险 | 优先处理方式 |
| --- | --- |
| 多人攻击/阶段语义错误，却显示零损 | 先差分后开放；未验证即明确边界 |
| 全局补丁或依赖导致非对称安装不同步 | 阶段 A 先验证；必要时拆分只读模块 |
| 旧目标在保路/早停中残留 | 小型目标反例 + 实际 SearchNode 路径验证 |
| 队友持续行动导致结果长期过期 | 一个活动请求、一个最新标记；快速临时结果但标明深度 |
| 队友无主动行动模型低估协同卡 | 明确模型边界；先不发明队友 DPS |
| 多人根体积增加、反复取消放大 GC | 共享不可变根、有限分支所有权、最终路线才存详细解释 |
| 过度扩大首版范围 | 先不主动用药、不自动执行、不开放未验证额外回合与他人选择 |

### 19.3 不建议首版加入的“聪明优化”

不建议先做学习队友牌风、推测队友每回合固定伤害、按人数摊敌人 HP、联合随机采样每个人的行动，或把两种目标塞进一棵共享可变树。这些优化会增加假设和验证成本，而不是解决当前最直接的语义缺口。

更深的预测也不天然更好。若 H 增加只是在放大“队友一直不出牌”的失真，而不能提升当前动作质量，应缩短窗口并保留有界的铺垫启发式，而不是追求看起来很长的路线。

## 20. 可直接交给实现者的任务说明

> 在固定的 CombatSolver 提交上新增实验性多人只读建议模式，沿用现有 `CombatRootSnapshot`、`SimulatedCombatState`、`CombatPredictionSimulator` 和 `CombatBeamSolver`。只展开本人的主动动作，但保留全体相关战场状态。以队友不再主动出牌/用药作为显式场景条件，正常执行已验证的多人被动与阶段结算。提供防住再输出、全力输出两个目标；默认统一完成三个敌方周期，并如实报告未完成深度。所有相关实机变化使旧建议失效，稳定后重算。首版不接管多人原生输入、不主动用药、不宣称团队最优或无条件安全。

建议动手顺序：先验证非对称安装和原生阶段/目标规则，再补多人回合推进与根指纹，之后接目标策略、时域、保路/支配和 UI。对单人路径做独立回归，默认行为不得变化。

### 20.1 审计命令起点

以下命令仅帮助在本地固定提交中定位，不能代替阅读与测试：

```bash
# 记录可复现基线
 git rev-parse HEAD
 git status --short

# 人数限制与隐式本地目标
 rg -n 'Players\.Count|LocalContext\.GetMe|\[_player\.Creature\]' src
 rg -n 'AdvanceRound|AdvanceRoundPlayerStart|ResolveRequestedPlayerTurnEnd' src/Search
 rg -n 'TargetsFor|TargetType\.AnyPlayer|TargetCombatId|ApplyForecastMove' src

# 目标、剪枝、完成条件与缓存
 rg -n 'CanStopAtHpTarget|StopAtAcceptableBattleHpLoss|IgnoreLongTermRewards' src
 rg -n 'FinalPlanOrdering|TranspositionLabel|Dominates|PlayerDead|TerminalStamp' src/Search
 rg -n 'ContinuationStamp|NetFullCombatState|Generation|DeployWhenReady' src/Runtime

# 按仓库当前本地配置准备好游戏与依赖后执行
 dotnet build CombatSolver.csproj -c Release
 bash tools/verify-refactor-boundaries.sh
```

构建所需本地游戏路径与工具参数应遵守仓库对应版本说明。`run-unattended-test` 的多人 fixture 需要先实现，本文没有虚构一个已经可调用的多人测试命令。

### 20.2 合并前的不可妥协条件

最终至少要证明：本地玩家识别正确、所有模拟不写实机、多人阶段/命中与原生一致、两套目标在中间搜索中真正生效、结果过期不会误用、正常战术终点不被误报失败、单人行为没有退化，以及“队友无需安装”的说法有真实安装组合证据。

**最终判断：这条路线值得做。** 它既不用解所有人的手牌，也不要求队友参与计算；现有代码已经提供了相当多可复用的状态与搜索基础。实现上应接受一个事实：可以省掉队友决策的组合复杂度，但不能省掉会影响本人结果的多人游戏规则。

## 附录 A：实施前必须从目标游戏构建核验的问题

这部分是具体的原生验证清单，不是假装已经查明的内部 API。

| 问题 | 需要取得的证据 |
| --- | --- |
| 本人提交结束意愿后，何时结算个人阶段、何时结算玩家方阶段？ | 原生函数调用顺序与双人阶段日志 |
| 队友已经结束/正在选择时，哪些字段是稳定且可捕获的？ | 原生状态、选择所有者与动作完成边界 |
| 不同玩家结束先后是否影响 Hook 顺序与 RNG？ | 交换顺序的对照回放 |
| 每类怪物攻击如何决定目标、每段是否重选目标？ | 对应行动命令与多目标差分 |
| 反伤造成攻击者死亡时，剩余目标/命中如何处理？ | 原生攻击上下文及真实结算结果 |
| 本人死亡、其他人存活时如何处理战斗终局和后续效果？ | 原生死亡/复活/胜负轨迹 |
| 额外回合是否改变全队阶段与其他玩家状态？ | 目标构建的实际机制，不沿用一代或旧攻略推断 |
| 当前客户端真实持有哪些队友牌/状态，哪些不能读取？ | 本地原生快照与协议的数据覆盖 |
| `NetFullCombatState` 是否覆盖多人阶段和待选状态？ | 字段与序列化审计；补足缺失项 |
| manifest 与 RitsuLib 对安装不一致如何处理？ | 实际加入和战斗结果、原生拒绝原因或同步校验 |
| Entry 中每个全局补丁是否保持多人原生确定性？ | 补丁作用域说明及启用/禁用对照 |

这些核验应优先于大规模适配协同卡牌。否则很容易在错误的世界推进规则上，积累一大批“看起来支持”的卡牌。
