## 来源与范围

用户要求继续合入官方最新版、发布本 fork Release，并使用 neat-freak 归档。本轮从干净的 `codex/multiplayer-advisor` / `1bca5f3f0de3edf94bcadbb2c4bb5bd4e661fe79` 开始；前版 fork 0.49.2，官方基线 `4b5537d00bfcbc822b2fbf78fc6da0c3e45ad161 / 0.49.1`。

一次无标签 fetch 固定本轮官方目标 `0d290fbee7e2779d2cebd8b8f652d82d00b6e8fc / 0.50.0`。读取上游 Release 与远端标签时，v0.50.1 尚未被两端使用；本 fork 使用 0.50.1。官方新 v0.49.2 与本 fork 旧同号标签来源不同，未抓取或移动官方标签；两份日志分开保存。没有移动其他 worktree，没有代发社区消息或操作官方发布渠道。

官方增量包括 0.49.2 的回合、金币、资源、反伤和内容 Mod 错误修复，0.49.3 的框架/局外兼容性修正，0.49.4 的上传引导及 PR #215/#217，0.50.0 的 PR #207/#211 与智能药水开局准入修复。上游的历史测试、性能数字、维护者决定和社区发布记录仅作为来源材料。

## 合并边界

- 单人候选、参数、计划、药水政策和运行库回退保持该官方版本行为。组件回复证书的原生 MVID 门禁原样保留。
- 多人根拒绝组件回复证书、已知回复策略和成长上界；政策清空单人 `PrimaryIncumbents`，Runtime 不获取该表，solver 禁用局部/共享胜利界及 Smart 节血剪枝。已有能力/计划/成长/脚本与前两回合探索隔离继续成立。
- 玩家 Hook 资格从多人独立停用集合统一到官方新增的 `SimPlayerCombatState.HooksActive`。根读取真实资格，Fork 复制，死亡清理后停用，多人治疗复活时恢复并使监听缓存失效；金币派发按分支资格在开始前固定全队来源，覆盖从死亡根复活的成员。
- 多人回合末在全队两阶段结算后共用 `ExtraTurnMirrors` 查询资格，逐参与者执行一次后置回调。佩尔之眼手牌耗尽归官方阶段镜像，移除旧预消费入口；不重复消耗额外回合来源。
- 多人手动请求、玩家输入、烘焙手套暂停边界、三周期贡献目标、十四敌方周期、普通预算乘二和固定预算不变。没有预测队友主动行为或接管队友操作。
- 结构门禁、架构、战斗语义/搜索/架构 skill 与第三方手册同步。多人原生连续请求 fixture 修正前次目录迁移遗漏的相对路径，恢复可重跑入口。

## 首次失败和未验证项

1. `GROUP-DEBUFF-ROSTER-CHANGE` 初始使用场景名作为种子，actual/simulated已相等，但随机自动攻击没有杀死首个敌人，未满足该fixture的必要条件。改用官方命令默认种子 `COMBATSOLVER`，同一生产源码触发所需死亡并通过原生完整状态与Fork断言。没有削弱断言或修改战斗语义。
2. `COMPONENT-HEALING-BOUND` 在本机返回 `native-version`：官方只认证MVID `8a76776c-0ce1-4d4f-90bd-8cce653dad8e`，当前macOS程序集不匹配。保留该拒绝和官方回退，不用改白名单取得通过；依赖相同前提的 `COMPONENT-SMART-BOUND`、`POTION-COST-INCUMBENT` 未运行。本机单人对照与Smart开局测试均通过，但不宣称启用证书分支已在本机验证。
3. 一次集成批次错误使用不存在的 `UPLOAD-GUIDANCE` 场景名，发现后主动终止启动器并清理实例，未接受其结果。改为真实入口 `CONTENT-MOD-FAILURES` 后完成反馈引导检查；首次操作回执保留。
4. 首次结构检查的两个匹配串没有遵循生产多行格式，修正规则后通过；没有改生产逻辑来适配静态检查。

真实联机、可见UI排版/帧时间、Windows/Linux/移动端运行、Windows MemoryCleaner、完整第三方栈、全部问题ZIP、干净安装和完整发布门禁未执行。缩小甲虫的特定原始失败仍待排查；本轮内容来源fixture通过不等于该原始问题已修复。上游“2–3倍/30倍”等历史数字没有写成本fork性能承诺。
